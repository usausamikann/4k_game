固定4Kリズムゲーム：Step 4.5（TPS切替・入力精度の可視化）と将来の高速入力設計
作成日：2026-10-13
対象：https://github.com/usausamikann/4k_game
位置づけ：memo/4k_game_implementation_plan_20261012.txt に対する補足メモ。
今回は実装方針の文書化が目的。Step 4.5を実装する場合も、高速入力バックエンドへの全面移行は含めない。

============================================================
0. 現状と方針
============================================================

・Step 4までに、Go + Ebitengine、JSON譜面、判定エンジン、中点分割、
  キー入力D/F/J/K、A/Bタイミング調整、SUDDEN+、8拍準備が実装されている。
・現在の入力取得は main.Update() の ebiten.IsKeyPressed(key)。
  internal/input.Tracker が前回状態との差分からPress/Releaseを生成し、
  internal/play.Session が同じ時間軸に変換してinternal/judgeへ渡す。
・Ebitengine v2.10.5 の IsKeyPressed は、単なる瞬間的なOSキー状態の参照ではなく、
  「そのtick中に押されたキー」を検出できる場合がある。ただし同じtick内の
  Press/Releaseの複数往復を、現在のTrackerで全件復元できるわけではない。
・既定60 TPSではUpdate周期の目安は16.67ms。240 TPSなら約4.17ms。
  ただしTPSはUpdateの目標頻度であって、OSイベント取得周期やタイムスタンプ
  精度が自動的に4.17msになる保証はない。OSイベントの取り込みと複数Updateが
  同じ描画フレームの中で処理されることもある。
・まず小規模な計測機能を追加してWindowsネイティブexeで比較する。
  明らかな入力欠落や不自然な判定ずれが残る場合に限り、別途イベント方式を設計する。
・SUDDEN+は現行の0.0～40.0（40.0で判定線まで遮蔽）が正式仕様。
  キー押下ハイライトの現行仕様も維持し、今回の変更対象にはしない。

============================================================
1. Step 4.5で実装するもの
============================================================

1-1. TPSの起動時切替
・例： -tps 60 / -tps 120 / -tps 240
・初期候補は240 TPS。従来動作との比較を容易にするため60/120も指定可能にする。
・Ebitengineのebiten.SetTPSを使い、ゲーム起動前に設定する。
・受理する値は当面60、120、240の3つに限定してよい。
・不正値は分かりやすいエラーとし、勝手に丸めたり無制限TPSにしたりしない。
・TPSに合わせて判定幅、ノーツの予定時刻、スクロール速度を変えない。
  いずれも既存のtime.Durationと実経過時間を使う設計を維持する。
・描画FPSとTPSは別概念。FPSを無理に240以上へ引き上げることは目的にしない。

1-2. 軽量なデバッグ表示
・任意の -debug-input オプション（名前は実装時に調整可）で表示を切り替える。
・少なくとも以下を表示する。
    Target TPS      : 起動時設定値
    Actual TPS/FPS  : ebiten.ActualTPS(), ebiten.ActualFPS() の参考値
    Last judge      : P-CLEAN / CLEAN / BAD / MISS
    Last hit offset : 符号付きミリ秒（例：-12.3ms FAST、+8.7ms LATE）
    Empty presses   : 既存統計
・offsetは内部の判定時間軸におけるResult.Offsetをそのまま表示する。
  A/Bの補正後の値であることを明記する。FAST=負、LATE=正。
・MISSは入力時刻・offsetを持たないため、直近MISSについて架空の数値を表示しない。
  必要なら「直近Hitのoffset」と「直近の確定判定」を別表示とする。
・ActualTPS/ActualFPSは瞬間的に揺れ得るため、性能の厳密な測定値と混同しない。
・表示は毎フレームの大量な文字列生成やログ出力を避ける。
  表示テキストの更新頻度を絞る、状態変化時だけ更新する等の簡単な対策を検討する。
・デバッグ表示オフ時は現行のシンプルなHUDを保ち、追加負荷を極力小さくする。

1-3. 既存挙動の維持（重要）
・internal/judgeの中点境界、±30/60/90ms、空打ち仕様、コンボ仕様は変更しない。
・A/B調整、SUDDEN+（0.0～40.0）、8拍準備、フォーカス喪失時の停止・復帰を維持。
・ゲーム時計をUpdate回数で進めない。実経過時間と単調時計を使う現行設計を維持。
・Press/Release取得方式自体は今回置き換えない。
・Step 5（PCMメトロノーム）は今回は実装しない。
・既存memo/を書き換えず、必要ならREADMEに起動引数と注意事項だけ追記する。

1-4. テストと完了条件
・不正TPS、正常TPSのパース・設定テスト。
・60/120/240のどの設定でも譜面予定時刻・判定結果が変わらないことを
  GUI非依存のテストで確認する。入力時刻が同じ人工イベントを使う。
・FAST/LATE符号、MISSにoffsetを捏造しない表示ロジックをテストする。
・go test ./...、必要ならgraphicsタグ付きテスト、go vetを実行する。
・Windows向けビルドを確認し、変更したファイルと検証結果を報告する。
・実機の押下精度、TPS実測、CPU使用率は、クラウドでのテスト成功とは別に記録する。
・Step 4.5の完了条件：TPSを切り替えて同じ譜面を再生でき、FPS/TPS・
  判定offsetを可視化でき、既存の判定結果を壊していないこと。

============================================================
2. Windows実機での比較・測定案
============================================================

・同じPC、同じexe、同じ入力デバイス・譜面・BPM・A/B設定で、
  TPS=60、120、240を比較する。
・確認項目：ActualTPS/ActualFPS、CPU使用率、取りこぼし、
  判定offsetの分布、FAST/LATE偏り、描画の引っ掛かり、フォーカス復帰。
・初めは短い低密度の譜面と同時押しで動作確認する。
・その後、BPM220・16分縦連（約68.18ms間隔＝毎秒約14.67打）を試す。
  元のノーツ同士の中点間隔は前後約34.09ms。
  ±30msのP-CLEAN境界も近く、入力時刻の揺れで隣のノーツの担当区間へ
  またぐ可能性がある点に注意する。
・可能なら連打時の「押下回数」と「認識Press回数」を区別して記録する。
  手押しだけでは実際の打鍵時刻・回数を厳密には検証できない。
・確認の際、キーを押している時間だけでなく、離している時間も重要。
  Update間でReleaseが見えないと、次のPressを独立に数えられない場合がある。
・性能値はWindowsネイティブexeで記録。WSL上のLinux版や仮想画面の測定を
  Windows実機の代用とはみなさない。
・60/120/240の結果を見て既定TPSを再評価してよい。
  240が常に優れる／十分だとは決めつけない。

============================================================
3. 将来検討：高速入力のイベント方式
============================================================

3-1. 変更を検討する条件
・240 TPSでも高速縦連のPress/Releaseが欠落する。
・押下時刻の量子化や処理遅延の揺れが判定を目立って不安定にする。
・音声を追加したStep 5以降、入力・映像・音声のずれをA/Bだけで
  安定して補正できない。
→ このような問題を再現・測定できてから新方式へ移行する。

3-2. 目指す構造
  OS/ウィンドウ側のキーイベント
       ↓
  入力バックエンド（Press/Release、物理キー、受信時刻を記録）
       ↓
  順序を保つイベントキュー（必要なら別スレッド）
       ↓
  Clock基準のゲーム時刻へ変換 ＋ A/B補正
       ↓
  既存のjudge.Eventの列
       ↓
  internal/judge.Engine.Process → 差分結果 → 描画

・描画フレームの回数とは独立に、検出できたPress/Releaseを個別に保持する。
・イベント順序は同時刻や同じキーの連打で特に重要。
・既存のjudge.Event（Lane/Time/Kind）、Sessionの時間軸、判定エンジン、
  Chart/NoteGroupを極力再利用する。
・受信バッファは再利用し、不要なgoroutine増殖・毎フレーム割り当てを避ける。
・ポーリングを高速化するだけでは「同じ取得間隔の複数エッジ」の復元には
  限界がある。イベントキュー化と単純なTPS増加は分けて考える。

3-3. Windows実装の候補と注意
・まずEbitengine公開APIで十分な情報を取得できるかを調査する。
  inpututil.IsKeyJustPressed/Releasedはtick単位の変化検出に便利だが、
  全Press/Releaseイベントの独立した時刻付きキューと同じものではない。
・必要ならGLFW/SDL等のウィンドウイベントの活用可能性を調べる。
  ただしEbitengine管理下のウィンドウ・イベントループへ安易に割り込まない。
・WindowsネイティブのRaw Input（WM_INPUT）等も候補だが、ウィンドウハンドル、
  WndProc、イベントポンプ、キーボードレイアウト・スキャンコードの扱い、
  スレッド安全性、Ebitengineとの競合に十分注意する。
・Raw Inputを導入しても「ハードウェア発生時刻が自動的に得られる」
  とは限らない。APIで取得できる時刻の意味と分解能を別に検証する。
・GetAsyncKeyStateを別goroutineで高速ポーリングするだけの方法は、
  キー状態の観測を速くする手段ではあるが、完全なエッジ列の取得保証にはならない。
・OS入力、ゲーム時計、将来の音声再生位置の時間軸を明示的に対応させる。
  単調時計を基本とし、イベント受信時刻と実際の物理的打鍵時刻を混同しない。
・起動直後の押しっぱなし、フォーカス喪失・復帰時のRelease、
  オートリピート、キー同時押し、キーボードのロールオーバー制限にも対応する。

3-4. 移行後に必須のテスト
・同一レーンでPress→Release→Pressが短時間に複数発生した場合、
  個々のイベントを欠落・合成せず順序どおりに処理する。
・同時刻イベントの安定順序、複数レーン同時押し、連打、
  OSキーリピート無視、フォーカス喪失、復帰直後の押しっぱなしを検証。
・Updateの頻度とイベントを渡すバッチサイズを変えても、
  元のイベント時刻列が同じなら判定結果が一致する。
・イベント時刻の逆行・未来イベントの保留・タイムスタンプ境界を検証。
・レース検出、Windows実機での入力遅延・CPU使用率を確認。
・旧バックエンドと新バックエンドの差を再現可能な入力列で比較する。
・必要なら測定ログに生のイベント時刻、変換後のゲーム時刻、
  判定Offsetを別々に出し、遅延の原因を追えるようにする。
