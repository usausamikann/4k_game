============================================================
1. 今回決めた基本方針
============================================================

・開発言語は Go。既存の Go + Ebitengine プロジェクトを利用する。
・4レーン（レーン番号 0～3）、4/4拍子を初期仕様とする。
・譜面の短い「パターン」は原則 1小節単位で保持する。
・1拍 = 960tick、4/4拍子の1小節 = 3840tick とする。
・tickは整数（原則 int64）で保持する。
・譜面中のノーツ位置はミリ秒ではなく tick で表現し、再生BPMから予定時刻へ変換する。
・パターン定義はソースコードに埋め込まず、Step 1 から JSON ファイルを読み込めるようにする。
・譜面データの読み込み／検証／BPM変換を描画・入力・判定エンジンから独立させる。
・今回必要なのは単一パターンの読み込みと時刻変換。ゲームプレイ、ノーツ描画、判定、ランダム連結はまだ実装しない。

補足：960tick/拍は配置の分解能。1tickごとにループしたりノーツを生成したりする必要はない。
960を採用する主な理由は、2分割・3分割・5分割などの細かなリズムや、将来的なパターン圧縮への対応余地を確保するため。

============================================================
2. Step 1 で実装するもの
============================================================

(1) 譜面データ型
・Note：レーン番号、パターン内tick位置など。
・Pattern：名前、長さ（初期は3840tick固定）、ノーツ列など。
・再生用ノーツ：ノーツID、レーン番号、予定tick、予定時刻。
・パターン自体の定義（不変データ）と再生用に確定したノーツを分離する。
・ノーツIDは再生用ノーツ生成時に一意かつ決定的に割り当てられればよい。
・Step 2以降の判定状態 Pending/Hit/Miss は今回実装しない。

(2) JSON読み込み
・patterns/sample.json を用意し、実際に読み込めるようにする。
・ファイルI/OやJSONのデコードは internal/chart のロード処理へ集約する。
・読み込み後は形式に依存しない Pattern として扱い、将来ほかのファイル形式も追加可能な構成にする。
・余計な抽象化やプラグインシステムは不要。Go標準の encoding/json を利用してよい。

JSON形式の例（ここでのtickはパターンの先頭からの相対位置）：
{
  "name": "sample",
  "length_ticks": 3840,
  "notes": [
    {"lane": 0, "tick": 0},
    {"lane": 1, "tick": 480},
    {"lane": 2, "tick": 960},
    {"lane": 3, "tick": 1440},
    {"lane": 0, "tick": 1920}
  ]
}

上記は一例で、必要に応じてフィールド名・内部構造を調整して構わない。
ただし、定義したJSON形式とtick規則はREADME等に明記すること。

(3) 譜面の検証
・レーンは0～3に限定する。
・長さは初期仕様で3840tickとする。
・ノーツのtickは 0 <= tick < 3840 を満たす。
  （次の小節の先頭は次のパターンに所属するため、終端3840は含まない。）
・同一レーン・同一tickの重複ノーツは不正としてエラーにする。
・異なるレーンでの同時tickは許可する。
・不正なJSON、範囲外の値などは意味の分かるエラーを返す。
・ノーツの入力順序に依存しないよう、必要に応じてtick／レーン順に整列する。

(4) BPM変換
・BPMを指定して、各ノーツの相対tickを予定時刻へ変換する。
・基本式：予定時間[秒] = tick × 60 / (BPM × 960)
・Goでは time.Duration 等の高精度な時刻型を利用する。
・各ノーツの絶対tickから直接計算し、丸め済みの1tick時間を繰り返し加算しない。
・BPMは正の値のみ受け付け、不正値はエラーにする。
・tick→時刻への丸め規則を明記し、テストで固定する。
・将来長い譜面に拡張する際に整数演算でオーバーフローしないよう配慮する。

例：BPM180の場合
・960tick（1拍） = 約333.333ms
・480tick（8分音符間隔） = 約166.667ms
・3840tick（1小節） = 約1333.333ms

(5) 単体テスト
・JSONの正常読み込みと各フィールドの一致。
・異なるレーンの同時押しデータを受け付ける。
・同一レーン・同一tickの重複を拒否する。
・レーン範囲外、tick範囲外、長さ不正、不正JSON、BPM非正値を拒否する。
・BPM120／180などでtick→予定時刻が正しく変換される。
・ノーツID・レーン・予定tick・予定時刻が決定的に生成される。
・ウィンドウを開かず go test ./... で検証できるようにする。

3. 将来の「パターン圧縮・連結」を見据えた設計
============================================================

将来のStep 7では、1小節分の同じパターンを時間方向に圧縮して、
1小節の中へ複数個配置する方式を採用したい。
例：1小節内で8分間隔のパターンを2回配置すると、各パターンは半小節に収まり、
元の8分間隔が16分間隔になる（同じBPMでの時間的な圧縮）。

候補：
・1倍：1小節に1個
・2倍：1小節に2個
・3倍：1小節に3個
・4倍：1小節に4個

ただし、倍速変換だけでは表現できないリズムもある。
8分、16分、24分などの異なるリズムを持つ独立パターンも作成可能な
「倍速再利用 + 個別パターン」の併用方式にする。

設計上の留意点：
・パターンの基準座標は常に1小節3840tickとして保持する。
・パターン原本は変更せず、配置時にtickの縮尺変換と開始位置の加算を行う。
・圧縮でtickが整数にならない場合の扱い（丸め／許可倍率の制限等）は
  Step 7で明示的に設計する。暗黙に整数除算で切り捨てない。
・異なるパターンの連結後は全体のノーツ位置を確定し、
  その後Step 2の中点判定境界を計算する。
・ランダム生成ではseedを保存して同じ譜面を再現可能にする予定。

★今回のStep 1で圧縮・連結・乱数選択を実装する必要はない。
将来困らないよう、パターン内tick座標と配置後の絶対tick座標を
区別できるデータ構造にしておけば十分。
