固定4Kリズムゲーム 実装方針・実装順
作成日：2026-10-12
対象リポジトリ：https://github.com/usausamikann/4k_game

【この文書の位置づけ】
・リポジトリmemo/の既存メモ3件を踏まえた、実装に向けた統合方針。
・特に、判定対象の対応付けは「元の譜面ノーツ間の中点分割」を採用する。
・判定幅の標準設定は JUSTICE CRITICAL ±30ms／JUSTICE ±60ms／ATTACK ±90ms とする。
・この文書の数値は自作ゲーム用の仕様であり、CHUNITHMの実機内部仕様を主張するものではない。
・既存memo/は残し、内容を変更する場合は明示的な指示を待つ。

============================================================
1. 実装すべきもの
============================================================

1-1. ゲームの目的・最初の完成形
・固定4レーン、4キーで操作する軽量なリズムゲーム。
・開発言語はGo、2D描画・ゲームループはEbitengineを第一候補とする。
・ユーザーがプレイ開始前に指定したBPMで動作する。
・短い譜面パターンを多数用意し、ランダムに連結して出題する。
・音声はメトロノームまたは単純なビープ音で十分。楽曲再生は初期要件にしない。
・ノーツは通常の単押し（TAP）のみ。ホールド、スライド等は初期実装から除外する。
・プレイ結果、判定数、タイミング誤差を確認できる。
・CPU使用率をできるだけ低く抑える。ただし実測と正しい判定挙動を優先し、根拠なく最適化しない。
・Windows実機で最終的にプレイして、入力精度・音声同期・CPU負荷を検証する。

最初のプレイ可能な中間目標：
・固定された短い譜面をBPMに沿って表示できる。
・4キーで判定できる。
・メトロノームを鳴らせる。
・結果を表示できる。
その後、外部パターンの読み込みとランダム連結を追加する。

1-2. 譜面データ・譜面生成
・譜面ノーツ：ID、レーン（0～3）、拍位置を持つ。プレイ用には予定時刻も確定する。
・パターン：長さ（拍数）とノーツ列を持つ。
・譜面は原則として拍位置を基準に保持し、指定BPMから実時間へ変換する。
・拍位置を整数tickで表現するか、float64で表現するかは初期設計時に決め、変換・丸め規約を固定する。
・同一レーン同時刻の通常ノーツは拒否、または明示的に統合する。別レーン同時刻は許可する。
・初期段階ではソース内の固定譜面を使用。その後JSON等のファイルからパターンを読み込む。
・ランダム連結ではパターンごとに開始拍を加え、全体の譜面時刻を確定する。
・乱数seedを保持して同じ譜面を再生成できるようにする。
・パターン接続部にも、同一レーンの連続ノーツ間の中点境界を作る。
・最初はプレイ開始前に全パターンを確定してよい。無限生成は後回し。

1-3. 判定エンジン（描画ライブラリから独立させる）
・4レーンそれぞれに時刻順の通常ノーツを持つ。
・不変の譜面定義と、プレイ中に変わるノーツ状態を分離する。
・ノーツ状態は最低限 Pending／Hit／Miss。
・判定結果は4種類：JUSTICE CRITICAL、JUSTICE、ATTACK、MISS。

【判定幅の標準設定】
入力時刻と予定時刻の差を offset とし、その絶対値によって成功判定を決める。
・|offset| <= 30ms：JUSTICE CRITICAL
・30ms < |offset| <= 60ms：JUSTICE
・60ms < |offset| <= 90ms：ATTACK
・これ以外：押下では成功判定を付けず、原則として空打ちとして無視。
・担当ノーツが受付期限までPendingのままなら自動MISSを付ける。

この30/60/90msは最初の標準設定で、各しきい値を設定データに分離して将来変更可能にする。
CHUNITHM風の約33.33/66.67/83.33msや、より厳しい・緩いプリセットの追加は将来の拡張とする。
最初から5段階の選択画面を作る必要はない。

【ノーツ対応付け：中点分割方式】
・同じレーン内で、元の譜面上の隣接ノーツの予定時刻T[i], T[i+1]から中点B[i] = (T[i] + T[i+1]) / 2を計算する。
・ノーツiの担当区間は [B[i-1], B[i])。最初・最後のノーツでは片側を無限遠とみなす。
・中点ちょうどの入力は、後ろのノーツに割り当てる。
・入力時刻が担当区間にあり、ノーツがPendingで、かつ|offset| <= 90msの場合だけ成功判定する。
・判定済みノーツの担当区間内で押しても、後続の未判定ノーツへ入力を回さない。
・判定が付いたあとも中点境界は再計算しない。元の譜面ノーツから固定する。
・成功判定は各ノーツにつき一回限り。一つの入力で複数ノーツを成功させない。
・トリルや同時押しを含め、中点はレーンごとに独立に計算する。
・中点分割により、ノーツ密度が高い場所では実際の受付区間が±90msより狭くなる場合がある。判定誤差自体を密度に応じて縮尺変換しない。

【自動MISS】
・ノーツの担当区間の右端（後ろのノーツとの中点）か、遅い側の成功幅+90msのいずれかで受付が終了する。
・中点がT+90ms以下なら、時刻が中点以上になった時点でPendingをMISSにする（中点は後続ノーツの区間）。
・それ以外は、時刻がT+90msを超えた時点でPendingをMISSにする（90msちょうどは成功可能）。
・自動MISS処理と、画面にMISS演出を出す時刻とは分離可能にする。

【時刻とイベントの扱い】
・入力イベントはPress/Releaseと発生時刻を持ち、同じ時間軸に変換して扱う。
・Pressの遷移だけを通常ノーツ判定に用い、押しっぱなし・OSのキーリピートは連打扱いしない。
・入力イベントを時刻順に処理し、各入力の直前にその時刻まで自動MISSを進める。キューの全入力を処理してから現在時刻まで自動MISSを進める。
・未来や過去へ勝手にイベント時刻を推定しない。入力APIから得られる実際の精度を検証する。
・時間は可能なら整数の高精度単位（time.Duration等）で扱い、中点の丸めルールを定める。
・オフセット補正と自動MISSは、整合した時刻軸で扱う。

1-4. 画面描画・ゲーム時計
・最低限、4レーン、判定線、落下するノーツ、押下状態を表示する。
・現在位置は「ノーツ予定時刻－現在時刻」から毎回計算し、フレームごとに位置を加算して誤差を蓄積させない。
・表示範囲のノーツだけを描く。
・ゲーム時計、描画、入力処理、判定処理の責務を分離する。
・描画FPSを上げるだけでは入力判定精度を保証できない。不要な無制限FPSは避ける。

1-5. キーボード入力
・4つのキーを4レーンに割り当てる（具体的なキーは後から決められるようにする）。
・PressとReleaseを区別する。
・短時間の連打や高速のPress/Releaseを取りこぼさないか、Windows実機で検証する。
・Ebitengineの入力APIで十分な精度が得られるかを早い段階で調べる。必要なら取得方法を再検討する。

1-6. メトロノーム・音声同期
・クリック音のPCM波形を生成する。
・BPMから各拍の絶対サンプル位置を算出し、波形を適切な位置へ配置する。
・time.Tickerで毎拍単発再生する方式を、精密なタイミングの基本実装にしない。
・音声出力バッファの遅延と、ゲーム時計・描画・入力の時間軸の対応を意識する。
・必要に応じて調整用オフセットを設ける（表示と判定を混同しない）。

1-7. ゲームの開始・終了・結果表示
・開始前にBPMを指定する。
・開始画面、プレイ中画面、終了・結果画面を実装する。
・JUSTICE CRITICAL／JUSTICE／ATTACK／MISSの件数を集計する。
・各入力のノーツID、入力時刻、offset、判定結果を記録する。
・空打ち・見逃しの数を記録する。スコア計算式は後から調整可能な設計にする。
・再現・デバッグ用に、譜面・seed・BPM・判定設定・入力イベント列等を保存できる構造を意識する（完全なリプレイUIは後回し）。

1-8. 自動テストと性能検証
・譜面生成・拍→時刻変換・中点計算・判定処理を、ウィンドウなしでgo testできるようにする。
・最低限、以下のケースをテストする。
  - 同一レーン1000/1100/1200msの境界1049/1050/1051msで担当ノーツが変わる。
  - 1000msを見逃した後、1090msの押下は1100msへの-10msで成功する。
  - 1000msを取ったあと1040msの余分な押下は1100msへ流れない。
  - 同一区間で二度押しても成功は一度だけ。
  - 複数ノーツ見逃し後も現在の担当ノーツへ復帰できる。
  - ±30/60/90msちょうどの判定、各境界の外側の判定。
  - 低密度譜面の成功受付範囲外は空打ちとして無視。
  - 不等間隔縦連、トリル、異なるレーンの同時押し。
  - 同一レーン同時刻の不正データを検出。
  - パターン接続部の中点境界が欠落しない。
  - 複数入力イベントを1フレームでまとめて処理しても結果が変わらない。
・CPU使用率、FPS、音声同期、入力遅延のばらつきをWindowsで実測し、必要な箇所だけ最適化する。

1-9. 初期実装の対象外
・ホールド／ロングノーツ、スライド、複雑なスキンやエフェクト、BGA。
・MP3等の楽曲再生、楽曲に合わせたタイムストレッチ。
・プレイ中のBPM変更、無限生成・ストリーミング譜面。
・ブラウザ版／WebAssembly、オンラインランキング。
・osu!maniaやMalodyとの完全互換判定。
・リプレイの表示UI、高度な設定画面。
これらはコアの動作とCPU負荷を確認してから検討する。

2. 実装の順番
============================================================

Step 0：Goプロジェクト初期化
・go.mod、main.go、.gitignore、README.mdなどを用意する。
・Ebitengineを導入し、起動するとシンプルなウィンドウを表示できるようにする。
・既存memo/は保持する。
・Go/Ebitengineのバージョン整合を確認し、go mod tidyで依存関係を確定する。
完了条件：go run .で最小ウィンドウが起動し、go test ./...が実行できる。
備考：2026-10-12時点のEbitengine v2.10.5はGo 1.25以上が必要。実装時に導入バージョンを確定する。

Step 1：譜面データ・BPM変換
・Note、Pattern等の基本データ型を定義する。
・まずコード内で固定の短い譜面を作る。
・拍位置を指定BPMに応じた予定時刻へ変換し、テストする。
完了条件：ノーツID・レーン・予定時刻が正しく生成される。

Step 2：中点判定エンジンと単体テスト
・レーンごとの中点境界を事前計算する。
・Pending/Hit/Miss、Press、空打ち、受付終了による自動MISSを実装する。
・判定幅30/60/90msを設定値として導入する。
・中点固定、押下のフォールバック禁止、境界の等号規則を実装する。
・人工の時刻・入力イベントで判定テストを作る。
完了条件：1-8の主要な判定テストを通過し、GUIなしで再現できる。

Step 3：4レーン描画とゲーム時計
・Ebitengineで4レーン、判定線、通常ノーツを表示する。
・現在時刻と予定時刻からノーツの位置を計算する。
・固定譜面を視覚的に再生する。
完了条件：指定BPMで譜面が流れ、描画更新に伴う時間誤差が蓄積しない。

Step 4：キーボード入力と判定の接続
・4キーのPress/Releaseを取得する。
・入力を判定エンジンに渡し、判定結果を画面に反映する。
・キーリピートや高速連打、入力APIの取得精度を確認する。
完了条件：実機でキーを押して通常ノーツを判定できる。高速入力時の制約を把握する。

Step 5：メトロノームの実装と同期
・BPMからPCMのクリック音列を作成する。
・ゲーム時計と音声の位置を対応させる。
・長時間の累積ずれと、出力遅延を確認する。
完了条件：数分間の再生で拍の累積ずれがなく、目・耳・入力の対応を調整できる。

Step 6：プレイ・結果画面、統計
・開始前のBPM指定、終了画面、リトライなどを実装する。
・判定件数、誤差、空打ち、MISSを表示・記録する。
完了条件：固定の短い譜面を最初から最後まで遊び、結果を確認できる。

Step 7：外部パターンとランダム連結
・JSON等で短いパターンを複数定義する。
・seed指定でパターンを選び、開始拍をずらして連結する。
・連結完了後に全体の時刻と中点境界を確定する。
完了条件：同じseed/BPM/パターン群から同じ譜面が得られ、接続部も正しく判定できる。

Step 8：性能・入力精度・同期の計測と改善
・Windows実機でCPU使用率、FPS、メモリ、入力・音声の遅延とばらつきを測定する。
・不要な毎フレーム全走査、メモリ割り当て、無制限FPS等を見直す。
・変更によって判定結果が変わらないよう回帰テストする。
完了条件：狙ったプレイ感と十分な判定精度を維持し、CPU負荷を合理的に抑えられる。

4. 開発運用・補足
============================================================

・ソースコードの編集、ロジック実装、自動テストはWSLやCodex Cloudなどで進める。
・Windows実機でのゲームプレイによる最終検証は別途必要。
・Codex CloudでGitHubの変更を作る場合は、作業ブランチ／Pull Requestでレビューし、取り込んでからWSL側でgit pullするのが安全。
・ゲームのために普段のWindowsファイル全体をAIの作業環境へ渡す必要はない。
・判定仕様と描画仕様を切り離すことで、将来プリセットや別判定方式を比較できるようにする。
・初期の優先順位は「判定の正しさと再現性 → 遊べる状態 → CPU負荷の測定と改善」。
