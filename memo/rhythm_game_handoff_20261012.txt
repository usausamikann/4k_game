固定4Kリズムゲーム開発・Malody解析・隔離環境の相談 引き継ぎ
作成日：2026-10-12
対象：このチャットで相談した内容。ゲーム実装・環境構築はまだ着手していない。

【1. 目的と現在の方針】
ユーザーは、軽量な固定4K（4レーン・4キー）リズムゲームを作りたい。
・事前に作成した多数の譜面／短いパターンからランダムに選んで流す。
・ユーザーが開始前に指定したBPMに合わせて再生する。
・音声はメトロノーム、または単調なビープ音でよい。
・主目的は低いCPU使用率。ブラウザ対応は将来の任意目標で、選定上の優先度は低い。
・Goで進める意向。2D描画・ゲームループの候補はEbitengine。
・最終的なプレイ確認はWindows実機で行う。
・AIにコード編集・実行まで任せたいが、普段のローカルファイルを削除・変更する事故を避けたい。
・今後のバイブコーディングにも使える隔離環境を検討中。VMかAWSかは未決定。

ユーザーはC++の競技プログラミング経験があり、Windows・VS Code・WSL Ubuntuを使用。
PCはIntel Core i7、RAM 16GB。Windowsエディション（Home/Pro等）とSSD空き容量は未確認。
既存WSLには競プロや国試DBなどの大切なデータがあるため、AI用にそのまま使うことは慎重に扱う。

【2. Malodyの静的解析】
提供された対象：
・Malody 4.3.7のmalody.exe
・config.json
・判定調整に関する画像
exeは実行せず、PE情報・インポート・文字列・逆アセンブルなどで解析した。
元のC++ソースやPDBは入手していない。解析内容を「完全に復元したソース」と扱わない。

確認した構成：
・ネイティブC++系の32bit x86 Windows実行ファイル。CLR/.NETアプリではない。
・PEのタイムスタンプは2019年9月。
・Cocos2d-x系のDirector、Scheduler、TextureCacheなどのクラス名がある。
・GLFW関連コード、OpenGL/GLEW、FMOD、BASS、FFmpeg、SoundTouch、Live2D関連が見つかった。
・UnQLiteの組み込みと、protobuf系の譜面・曲・スコア用データ型が見つかった。
・複数の譜面形式／ゲームモード、BGA・動画・エフェクト・スキンを支える構成。
ライブラリが存在することだけで、すべてが常時動いているとは断定できない。
C++や古い年代という理由だけでCPU負荷の原因を決めない。

特にフレーム制御で確認したこと：
・fps_unlimitがtrueの経路では、1000Hz相当の更新間隔をDirectorへ渡す処理がある。
・falseの経路でも、360Hz等の高い目標値になる処理がある。
・これはコード上の目標間隔であり、実測FPS／CPU負荷の保証ではない。
・設定falseでも「60FPSに制限される」とは言えない。
同じ譜面でFPS、CPU、BGA・3D列・エフェクトの設定を比較するのが原因確認に有用。

config.jsonで相談した主要値：
fps_unlimit=false、show_fps=false、show_bga=true、use_column3d=true、
effect_level=2、user_offset=0、graphic_offset=-8、user_judge_level=3。
個人情報・認証トークンは引き継ぎに含めない。未知の設定項目の意味を名前だけで断定しない。

Malody 4.3.7の通常Key判定について、逆アセンブルで得た判定幅：
各値は中心から片側の幅、単位ms。
          BEST    COOL    GOOD
A          56      96     130
B          46      86     120
C          36      76     110
D          28      68     102
E          20      60      94

根拠：
JudgeKeyの基準値36/76/110に、
レベル0～4で +20/+10/0/-8/-16 を加える処理を確認した。
A/BのUIラベルとインデックスの対応も確認した。
設定user_judge_level=3は、この対応ではD。
これは添付exeの通常JudgeKeyの結果に限定する。
JudgeKeyFairという別クラス、ホールド、他モード、他バージョンにはそのまま適用しない。
早すぎる入力を無視する範囲やMISS処理は別にあり、全挙動をこの表だけで表せるわけではない。
ネット上のA/Bの数値と異なる資料があるため、バージョンと判定クラスを明示する。

【3. osu!maniaと遅延の整理】
公式公開リポジトリはppy/osu（主にosu!lazer、C#）。
旧stableとlazerを混同しない。参考になるのはManiaRuleset、
DrawableManiaRuleset、ManiaHitWindows等。基盤はosu-framework。

stable通常譜面・通常条件の公称片側判定幅（ms）：
PERFECT：16
GREAT：64 - 3×OD
GOOD：97 - 3×OD
OK：127 - 3×OD
MEH：151 - 3×OD
丸め、遅い側の自動MISS、ホールド、変換譜面、MOD等で扱いが変わる。
lazerでは最高判定などの実装が異なり、Classic/ScoreV2等も関係するため、
「osu!mania全体の唯一の判定幅」として説明しない。

キーボード遅延：
・物理的な打鍵からOS／ゲームが入力を受け取るまでに遅延がある。
・平均的で一定のずれはオフセットで補正できる。
・入力遅延のばらつき、取りこぼし、押してからキー音が鳴るまでの遅延は、
  判定オフセットだけでは解消できない。
・音声出力遅延、表示遅延、入力遅延、プレイヤーの癖が混ざるため、
  プレイ結果だけからキーボード単体の遅延を特定するのは難しい。
・Windows Raw Inputも、物理スイッチの作動時刻を自動で取得する万能な方法ではない。
・「音に対する譜面位置」と「表示に対する判定時刻」の調整は、別の関係を変える設定。
  耳と目にそれぞれ独立した二つの判定器がある、という意味ではない。
・オフセットの正負方向はゲームごとに確認する。

【4. 自作ゲームの設計方針】
音声は一般的な曲付き音ゲーより簡単にできる。
MP3デコード、曲ごとの頭出し、タイムストレッチ、動画同期等を初期実装から省ける。
ただし音声時計と入力・表示の同期は残る。

譜面は絶対秒ではなく拍位置を基準に保持する。
例：
Note { Beat float64, Lane int }
Pattern { LengthBeats float64, Notes []Note }
BPM=Bのとき、拍bの予定時刻は b×60/B 秒。
細かい音価を厳密に表す必要があれば、整数tick等も検討する。

メトロノーム：
・短いクリック波形を用意し、連続PCMストリームの所定のサンプル位置に置く。
・サンプルレートfsで拍bの位置は round(fs×60×b/B)。
・各拍の絶対位置を計算し、丸めた拍間隔を延々加算して誤差を蓄積させない。
・time.Tickerの通知を受けて毎拍Playする方式は、音の配置精度を得る基本方式にしない。
・「生成／送信したサンプル数」と「実際に聞こえている位置」は異なる。
  バッファと音声出力遅延を考慮して時計を設計する。

描画：
・ノーツ位置は予定時刻と現在時刻の差から計算する。
・フレームごとに一定距離移動させて、時間誤差を積み上げない。
・画面近くのノーツだけ描く。
・入力取得、ゲーム更新、描画の頻度は役割を分けて設計する。
・60Hzごとにキー状態を確認するだけなら確認間隔は約16.7ms。
  高い判定精度が必要な場合は、入力APIと時刻取得方法を初期段階で検証する。
  Ebitengineを使うだけで高精度入力が自動的に保証されるわけではない。

判定：
・各レーンの次の未処理ノーツを対象にする。
・入力時刻－予定時刻をタイミング誤差として評価する。
・見逃したノーツは自動MISS。
・譜面の定義と、プレイ中の可変状態を分ける。
・描画ライブラリから独立した判定ロジックにする。

ランダム接続：
・固定の拍数を持つパターンを、開始拍を加えて連結する。
・次のパターンは画面に現れるより前に決める。
・境界のノーツ間隔、同時押し、将来のホールド重複、難易度分布を確認する。
・乱数seedを保存できると、同じ出題の再現や不具合調査に役立つ。
  seed保存は今後の設計候補で、実装済みではない。

CPU負荷を抑える方針：
・毎フレームの不要な確保、全譜面の走査、ファイル読込を避ける。
・配列と音声バッファを再利用し、譜面解析はプレイ前に行う。
・ノーツごとのgoroutine等は初期構成で必要ない。
・無制限FPSにせず、要求精度と負荷を実測して頻度を選ぶ。

【5. 言語選定と実装順序】
Goは今回の小さな4KゲームのCPU負荷という目的には妥当、という判断。
・Go：作りやすさ、Ebitengineによる2D／WebAssembly対応。GCと入出力APIを確認する。
・Rust：GCなしで処理・メモリを細かく制御できるが、学習や統合作業が増える。
・C#：ゲーム開発の選択肢があり、osu!コードを参考にしやすい。
・C++：既習なら有力。古いMalodyが重いことはC++全般の欠点ではない。
・Haskell／MoonBit：不可能ではないが、今回の実用目標では優先度を下げた。
性能の順位を実測したわけではない。問題が出たら言語変更より先に、
更新頻度、描画量、確保、入力・音声ライブラリを調べる。

提案した実装順：
1. ウィンドウ、4レーン、判定線、キー押下／解放。
2. コード内の短い固定譜面とゲーム時計。BPMから時刻へ変換して表示。
3. PCMメトロノームと同期。数分動かしてずれを検証。
4. 通常ノーツ判定、早い／遅い表示、自動MISS。
5. 最小限のスコア、開始・終了・結果画面。
6. JSON等の譜面ファイル、パターンのランダム連結。
7. 設定・演出・保存など。

最初の仮組み範囲：
固定4K、通常ノーツのみ、開始前にBPM指定、短い固定譜面、
メトロノーム、判定、結果表示。
プレイ中BPM変更、一時停止、ホールド、複雑なスキン等は後回し。

初期ファイル構成案：
main.go：起動
game.go：画面状態、更新、描画
chart.go：譜面、拍→時刻
clock.go：プレイ時刻と開始・終了
audio.go：メトロノーム
input.go：キーと入力時刻
judge.go：判定、MISS、スコア

【6. AIを使う開発環境と隔離】
このチャットの実行環境はユーザーのWindowsとは別。
Windows実機のCPU負荷、音声遅延、打鍵感を直接検証する環境ではない。
コード作成やロジック検証は隔離環境で行い、最終評価を実機で行う方針。

候補：
・VS CodeのCodex拡張：開いた環境で編集・コマンド実行。
・Codex CLI：起動した環境で編集・コマンド実行。
・ローカルのCodexサンドボックス：作業フォルダ外への書込等を制限。
・専用VM：普段のWindowsと別OS／仮想ディスクに隔離。
・クラウド環境／AWS：PCとは別の計算機で作業。

注意：
・プロジェクトフォルダを分けるだけではアクセス権限の隔離にならない。
・Full access等で境界を外さない。
・標準のWSLは/mnt/cからWindows側ファイルへアクセスできる。
・WSL2はVM技術を使うが、標準設定はWindowsとの連携を重視したもの。
・専用WSLで自動マウントや相互運用を制限する方法はあるが、
  それだけで独立VMと同等の隔離が保証されるとは扱わない。

専用VM案：
・ホスト＝普段のWindows、ゲスト＝VM内のUbuntu等。
・VM内にGo、Git、エディタ、Codexを入れる。
・普段のフォルダ／ドライブ全体を共有しない。
・共有クリップボード、ドラッグ＆ドロップ等は必要になるまで無効。
・AIは通常ユーザーで動かし、VM内でもプロジェクトの権限制限を使う。
・インストール等の管理作業は人が分けて行う。
・必要な認証情報のみ渡し、本番環境や広い権限を持つ鍵を持ち込まない。
・NATは候補だが、NATだけで家庭内LAN／ホストへの通信が完全に遮断されるわけではない。
・コードはGit、環境はスナップショット、消失対策はVM外バックアップ。
・スナップショットはバックアップそのものではない。
・Docker／Dev Containerは環境再現に便利だが、共有マウントや強い権限に注意。
・Windows Sandboxは使い捨ての確認環境。Homeは非対応で、継続開発には保存の工夫が必要。

PC RAM16GBでのVM開始案（最低要件ではない）：
Ubuntu LTS、RAM4GB程度、仮想CPU2個、可変容量ディスク上限60GB程度。
Windows Pro等ならHyper-Vが候補。HomeならVirtualBox等を検討。
既存WSL2との共存条件、Windowsエディション、空き容量を確認してから選ぶ。
VMはホストの資源を使うため、PC負荷を下げる手段そのものではない。

【7. AWSという選択肢】
Amazon EC2は、AWS上の仮想マシンを借りるサービス。
・Ubuntu等のEC2内でGo、Git、Codexを動かし、編集・ビルド・テストできる。
・手元のPCはエディタ／接続用クライアントを動かす程度で済み、
  ローカルVMのRAM負担を避けられる。
・AIモデル自体をEC2で実行する意味ではない。
  通常はCodexクライアントと開発ツールを置き、モデルへサービス経由で問い合わせる。
・EC2は渡したファイルと認証情報を操作できる。隔離に加えて権限の制限が必要。
・VM稼働、ディスク、通信、IPv4等の料金を確認する。
・接続を切るだけでは停止しない。EC2の停止操作が必要。
・停止後も保存ディスク等の料金が残る。
・リージョン、OS、インスタンス種類、稼働時間で見積もる。
  このチャットでは具体的な料金／インスタンスを決めていない。
・AWS管理者権限をAIの開発用環境へ渡さない。
・リモート画面でのプレイは通信遅延が混ざるため、音ゲーの最終評価はローカルWindows。
