4k_game — Step 5.5 キー音（keysound）実装引き継ぎ仕様 / 音源選定待ち
作成日：2026-10-18
対象：https://github.com/usausamikann/4k_game
位置付け：仕様・実装方針のメモ。今回のPRはドキュメントのみで、キー音は未実装。

【最重要：現時点で確定した事項】
・キー音はメトロノームと独立した、実際のキー押下に応じる効果音。
・モードを3種類用意する。
  1. Off：キー音なし（現在の挙動）。
  2. Unified：4レーンすべて同じ、選択した1音源で発音。
  3. Per-lane：レーン0/1/2/3にそれぞれ個別の音源を割り当てられる。
・Per-laneでは4レーンに異なる音を設定でき、同じ音源を複数レーンへ指定することも妨げない。
・短いメトロノームしかないゲームだからこそ、4レーンの打音を自由に選んで楽しめるようにしたい。
・キー音の候補・具体的ファイル・ライセンスの確認・デフォルト音色は「まだ選定されていない」。
  既存のメトロノーム用OGG 5種をキー音として採用する決定もしていない。
・Step 5.5の実装では、ユーザーが音源を決定・提供するまで、勝手に音源選定、
  架空のファイル名、代替ビープ音、サンプル音源のコミットをしないこと。
・今後の実装も別PRで行う。本書追加PR自体はソース変更を含まない。

============================================================
1. 機能要求
============================================================

1-1. Off / Unified / Per-lane
・Off：キー音を一切出さない。メトロノームは通常どおり鳴る。暫定の既定モードはOffとし、
  音源未選定でも現行の起動動作を壊さない（最終既定値は実装時に確認可）。
・Unified：選択した音源1種類を全4レーンで鳴らす。
・Per-lane：4レーンそれぞれに独立した音源IDを設定できる。物理キー名ではなく
  レーン0..3に対応させる。-keysによるD/F/J/K等の変更後もレーン割り当ては不変。
・メトロノームの選択・音量・音色とキー音の選択は互いに独立させる。
・Step 5.5ではGUIは必須とせず、起動引数／設定構造から選べればよい。
  CLIの命名候補は -keysound-mode off|unified|per-lane、
  -keysound-sound <sound-id>、-keysound-lanes <id0,id1,id2,id3>。
  これは「提案」であり、既に実装された引数ではない。実装時にREADMEへ正式な値を記載する。
・不正なモード、無効な音源ID、不足したレーン割り当てを黙って代替せず、
  説明付きエラーにする（Off時の無関係な引数の扱いは実装時に明文化）。

1-2. 音を鳴らすイベント
・「実際のPress」に対して反応する打鍵音が目標。譜面の自動MISS、Release、
  押しっぱなし、OSキーリピート、フォーカス復帰直後に保持されているキーで鳴らさない。
・判定に成功したときだけ再生する方式にはしない方向を推奨。
  空打ちでもキー音を鳴らすかどうかはユーザーに最終確認する（暫定案：鳴らす）。
  判定結果と発音イベントを結びつけると音声遅延や判定変更の影響が出るため、
  既存TrackerのPress遷移を可能な限り共有し、入力を二重にサンプリングしないこと。
・COUNT/SILENT中の物理Pressにキー音を許すかも未確定。
  暫定案は準備時間中も実際のPressに反応（メトロノームのSILENTは「自動クリックなし」を意味する）。
  PLAY開始前のノーツへの早押し許容（現行仕様）と矛盾しないよう決定する。
・無音デバイス待機中、ウィンドウ非フォーカス中、抑止された保持キーでは発音しない。
・同時押しでは指定した各レーンの音を再生する。16分縦連・階段でも
  各Pressに反応し、前の音の尾を不必要に打ち切らない。

============================================================
2. 音源が決まってから着手すること（今は未着手）
============================================================

・候補音源のライセンスと再配布条件、配布元、元ファイル名を記録する。
  不明な権利の音源をリポジトリへ同梱しない。
・ユーザーに候補を聴き比べてもらい、採用可能な音源IDを確定する。
  Unified用と各レーン用の選択可能リストは共通にしてよい。
・短くアタックが明瞭で、連打に耐える音を優先。長い先行無音、ピーク、音量差、
  モノ／ステレオ、サンプルレート、末尾の長さをチェックする。
・元音源はできるだけ変更せず保存し、デコードや先行無音補正は起動時に行う。
  メトロノームの閾値ベースの補正を無条件で使い回すと音色が変わる可能性がある。
  音ごとの補正量・基準を記録し、音のアタックを削らないようにする。
・Ebitengine既存Contextに合わせ、キー音を48kHz/stereo/F32等の共通フォーマットへ変換する。
  重複選択した音源は一回デコードして共有し、Pressごとにファイルを開いたりデコードしたりしない。

============================================================
3. 技術設計上の必須条件
============================================================

・既存Step 5のメトロノームは単一の連続PCM Reader/Playerを使用している。
  4 COUNTクリック→4拍の自動無音→PLAYで四分クリックという配置、
  拍頭アクセントなし、絶対サンプル位置、停止復帰バッファ保持を変更しないこと。
・Ebitengineのaudio.Contextは1プロセスに1個だけ。audio_setup.goで生成している
  既存Contextを使い回し、キー音追加のためにNewContextを再度呼ばないこと。
  複数の再生音が必要なら、同じContextからPlayerを構築する案、
  あるいは同一音声ミキサーへ混合する案を比較し、低遅延・軽量・安全な方を選ぶ。
・既存メトロノームの音声ストリームを安易にSeek/再作成しない。
  Pressイベントが音声バッファの先読み位置より過去に届く可能性を考慮し、
  押下レスポンスは固定拍配置とは異なるリアルタイム音声処理として設計する。
・音声を発音するために判定エンジンの時間軸・A/Bオフセット・中点規則を改変しない。
  既存 -debug-audio のClock/Positionは「参考値」で物理出音時刻ではない。
  低遅延を断定せずWindows実機で打鍵→出音を検証する。
・音量差・多重発音でクリッピングしないよう合理的なヘッドルームを確保する。
  同時発音数・プレイヤー／ボイス再利用・解放方法に明示的な上限を設け、
  速い連打でもPlayer生成やデコードなどを毎Pressで無制限に行わない。
  優先度が必要な場合のボイス枯渇方針（古い音の停止、音を落とす等）は文書化する。
・音声処理のためにUpdateを長くブロックしない。通常フレームで重い割り当て、
  新規goroutineの乱立、音声バッファ全文コピー、無限キュー等を避ける。
・フォーカスを失った場合、メトロノームとキー音を確実に停止する。
  復帰時にはキー音の残響／バッファから不意に音が再発しないよう扱いを明示し、
  メトロノームの再開位置・キー保持抑制は従来どおりにする。
・同じ物理Pressで音が二度鳴らないことを保障する。
  Ebitengine標準キーAPIの高速Press/Release検出制約は残るため、
  キー音導入が入力検出精度を改善したと主張しないこと。
・音源未選定の段階で音源IDや起動例を仮に決めて実装済みと書かないこと。

============================================================
4. 実装時のテスト・受入条件
============================================================

Headlessテスト（可能な限り入力・音声デバイス非依存）：
・Offでメトロノームのみ・キー音なし。
・UnifiedでどのレーンのPressでも同じ音を要求。
・Per-laneでレーン0〜3の指定音へ正しく振り分ける（同一音指定も許可）。
・Release／長押し／キーリピート／保持キー抑止／フォーカス喪失では鳴らない。
・空打ち・準備中の扱いは確定仕様に従う。Hit/Miss処理と独立であること。
・同時押し、BPM180/220での16分縦連・階段相当の人工イベント列。
・多数の連打でも有限メモリ・有界ボイス数、重複デコードなし。
・不正CLI設定は適切にエラー。音源未配置・デコード失敗も説明付きエラー。
・メトロノーム波形、COUNT/SILENT/PLAY、A/B、TPS、SUDDEN+、
  Judge、Clock、Step 5.1診断・Alt+Tabの既存テストに回帰なし。

実装時の検証：
go test ./...
go test -tags=graphics ./...
go test -race ./internal/...
go vet ./...
Windows amd64向けビルド。
音声デバイス統合テストが実行可能なら実施。ただしnull出力は実出音の代わりにならない。

Windowsネイティブの実機受入：
・UnifiedとPer-laneで音色を選び分けられる（Offは無音）。
・高速連打・同時押しで明らかな欠落や耳障りなクリッピングがない。
・キー音がメトロノームを不規則にしたり、TPS/FPSを大きく悪化させたりしない。
・Alt+Tab時に音が止まり、復帰時の押しっぱなしキーから誤発音しない。
・打鍵から聞こえるまでの応答遅延とCPU／メモリ使用量を確認する。
・WSL/WSLgでは過去に音声の体感遅延・Player.Position参考値の揺れが観測された。
  この結果だけでLinuxネイティブ全体の問題とみなさず、Windowsネイティブを先に評価する。
