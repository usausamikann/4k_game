固定4Kゲーム：中点で判定範囲を分ける設計とosu!lazerとの比較
作成日：2026-10-12

【結論と今回の前提】
採用候補は「同じレーンの隣り合う譜面ノーツの予定時刻の中点で、入力を受け持つ範囲を固定する」方式。
境界は未判定ノーツの間ではなく、元の譜面ノーツの間で決める。前のノーツを取った・見逃したという理由で境界を動かさない。
これにより、前のノーツを見逃しても次を少し早く押して復帰しやすくなる。一方、前のノーツを大きく遅れて押すと、次のノーツを取ることがある。
「ミスハマりしない」保証ではないが、古いノーツへの吸着と、判定済みノーツから次への入力の流れ込みを抑えられる。

これはCHUNITHMの非公式解説にある中点分割の考え方を、通常ノーツだけの固定4K向けに具体化した自作仕様案。CHUNITHMの現行内部実装を再現したものではない。
特に、中点ちょうどの所属、自動MISSの確定時刻、空打ち無視はここでの提案であり、CHUNITHMの確認済み仕様として扱わない。
比較対象のosu!は、公開コードを確認したosu!lazer（ppy/osu）。旧stableやホールドの全挙動を含む比較ではない。

【1. 数学的な定義】
同じレーンの通常ノーツを予定時刻T[0] < T[1] < ...で並べる。
隣のノーツとの境界B[i] = (T[i] + T[i+1]) / 2。
ノーツiの担当範囲は [B[i-1], B[i])。
最初のノーツの左境界は負の無限大、最後の右境界は正の無限大と考える。
中点ちょうどは後のノーツに割り当てる。左右どちらを選ぶかは設計上の選択だが、必ず一意にする。

担当範囲に入っていても、無制限に成功するわけではない。
入力時刻t、誤差d = t - T[i]、最大の成功判定幅Wについて、|d| <= Wも必要。
実際の受付範囲は「担当範囲」と「[T[i]-W, T[i]+W]」の共通部分。
成功評価は通常通り|d|から決める。密度に合わせて誤差を倍率換算しない。

例：T=1000、1100、1200ms、W=120ms。
中点は1050、1150ms。
中央の1100msノーツは1050ms以上1150ms未満を担当する。
1000msノーツの担当範囲は1050ms未満、1200msノーツは1150ms以上。両端も成功幅との共通部分に限定する。

【2. osu!lazerとの対象選択比較】
osu!lazerのOrderedHitPolicy.IsHittableは、次の生存中ノーツのStartTimeに達したら前のノーツへの打鍵を拒否する。
HitObjectContainerでは早いノーツが先に入力を処理する。
したがって前が未判定で受付可能なら、次に近い入力でも前が取ることがある。
後続ノーツが成功すると、OrderedHitPolicy.HandleHitが先行未判定ノーツを強制MISSにする。
自動MISS期限は通常ノーツの場合、最も広い成功判定Mehの遅い側の幅を超えたとき。

以下の比較は対象選択を分離して見るためのもの。両方式が同じ成功幅W=120msを持つと仮定し、前の1000msノーツが未判定、次が1100msとする。osu!の実際の判定幅の数値ではない。
  入力1040ms：中点方式は1000msへの+40ms。lazer方式も前が受付可能なら1000msへの+40ms。
  入力1050ms：中点方式は1100msへの-50ms。lazer方式は1000msへの+50ms。
  入力1060ms：中点方式は1100msへの-40ms。lazer方式は1000msへの+60ms。
  入力1090ms：中点方式は1100msへの-10ms。lazer方式は1000msへの+90ms。
  入力1100ms：両方式とも1100msへの0ms。lazerでは前がnote lockで拒否される。
  入力1110ms：両方式とも1100msへの+10ms。
この表の各行は独立した状況。上から順に連続で押すリプレイではない。

【3. 考えられる挙動】
3-1. 見逃し後の早押し復帰
1000msを抜かし、1100msを1090msで押すと、1100msへの-10msで成功する。
lazer方式では前が未判定・受付可能なら前への+90msになる。
中点方式は、抜かした後の早押しからも復帰しやすい。

3-2. 大きな遅押しが次のノーツになる
1000msを1060msで押したつもりでも、境界1050msを超えているため1100msへの-40msになる。
入力の意図を読む方式ではなく、時刻で固定的に割り当てる方式。遅い側の許容が短くなるトレードオフがある。

3-3. 前を取った後の余分な入力は次を取らない
1000msを正しく押した後、1040msにもう一度押しても、その時刻は1000msの担当範囲。
担当ノーツが判定済みだから空打ちとして無視する。1100msへ繰り越さない。
「未判定ノーツの中で最も近いもの」を再検索すると1100msを取ってしまい、この挙動を維持できない。

3-4. 二重入力も一ノーツにつき一成功
同一担当範囲で最初の押下を成功させた後は、他の押下を無視する。
ただし余分な入力が境界を越えた後なら次を取る可能性がある。中点方式だけで連打の有利さを完全に消せるわけではない。

3-5. ノーツ間隔が短いほど低評価の領域が削れる
間隔Dの等間隔縦連では、中央の各ノーツの担当範囲はおおむね±D/2。
例えば最高判定が±20ms、最大成功幅が±120msの場合：
  D=100ms：担当範囲は[-50,+50)ms。±50msを超える低評価領域は使われない。
  D=40ms：担当範囲は[-20,+20)ms。受付できた入力はすべて最高判定になる。
これは100msの誤差を20msへ縮めているのではなく、遠い入力がそのノーツへ割り当たらなくなるということ。
通常ノーツのみで空打ちを罰しない場合、細かな連打で各担当区間を一度ずつ押せると高評価を取りやすい。実際にそうなるかは押下頻度、解放、入力取得精度にも依存する。

3-6. 疎な譜面では元の成功幅が優先
ノーツ間隔D > 2Wなら、成功範囲の間に空白が残る。
例えばW=120ms、ノーツ1000/1500msでは、1120msを超えて1380ms未満は両方の成功範囲外。
中点1250msの前後で担当が変わっても、その空白の入力は無視する。

3-7. 不等間隔では左右非対称
同一レーン1000、1100、1500msなら、1100msノーツの担当範囲は[1050,1300)ms。
W=120msなら実際の受付は[1050,1220]ms。
早い側は50ms、遅い側は120msまで。各ノーツの前後間隔が別々に効く。

3-8. 複数の見逃しでも対象は今の区間
過去に未判定ノーツがいくつ残っていても、入力はその時刻の担当ノーツにしか渡さない。
過去ノーツを一つずつ入力で消費しない。ただし実際の入力リズムがずれているケースや、境界を越える余分な打鍵による取り違えまではなくならない。

3-9. トリルの境界はレーン単位
左右交互に全体75ms間隔で出るなら、同じレーンの間隔は150ms。
各レーンの担当範囲は隣接する同レーンノーツから計算する。全体の75msから一律±37.5msとしない。
他レーンの同時押し・見逃しはこのレーンの境界を変えない。

3-10. BPM上昇で受付幅が狭くなる
BPMを上げて同じパターンを速くすると、ノーツ間隔と中点までの距離が短くなる。
固定msの最高判定幅を維持したままでも、低評価領域が消えることがある。
結果をBPM間で比較するなら、誤差ms、押下回数、空打ち数も残すとスコアだけの比較より分かりやすい。

【4. 自動MISSの仕様案】
ノーツの受付が終了したら、そのノーツは後から成功しない。
右側の中点RがT+W以下なら、t >= Rで未判定をMISSにする。Rちょうどは次の担当。
T+WがRより手前なら、t > T+Wで未判定をMISSにする。t = T+Wは成功幅の端として受付可能。
最後のノーツは右側境界がないため、t > T+WでMISS。
ここは自作仕様としての選択。CHUNITHMがこの時点でMISS表示を出す、と確認したわけではない。
判定確定と演出の表示は分けてもよい。見逃したノーツがいつ画面から消えるかは、受付終了時刻を変えずに調整する。

【5. 実装の核心：譜面の固定区間を引く】
準備：
・BPMと拍位置からノーツ予定時刻を確定する。
・レーンごとに予定時刻順へソート。
・隣り合う元の譜面ノーツから全中点を計算。
・譜面データとPending/Hit/Missなどの可変状態を分ける。

押下処理の擬似コード（通常ノーツのみ）：
  i = upper_bound(boundaries[lane], corrected_input_time)
      // 中点 <= 入力時刻の個数を返す。中点ちょうどは後のノーツへ。
  if レーンにノーツがない: return
  if state[i] != Pending: return
  offset = corrected_input_time - notes[i].scheduled_time
  if abs(offset) > max_success_window: return
  result = grade(abs(offset))
  state[i] = Hit
  record(note_id, input_time, offset, result)

担当ノーツが処理済みでも、別のノーツへフォールバックしない。
一つの入力から成功させるのは、そのレーンの一つだけ。
自動MISSは別に時刻順で処理。これにより入力によって先行MISSをまとめて処理する仕組みは必須ではなくなる。
二分探索なら入力ごとにO(log N)。時刻が単調な通常プレイなら区間ポインタでもよいが、巻き戻し・リトライではリセットが必要。
未処理ノーツの先頭ポインタと、入力時刻の担当区間ポインタは意味が異なる。混同しない。

【6. 実装時の注意点】
6-1. 判定幅内の入力MISSは初期仕様では設けない
成功範囲外の入力は空打ちとして無視し、ノーツを消費しない。
広い早押しMISS幅を追加すると、未来のノーツを先に消費する別種の連鎖を作り得る。
連打を抑えたければ、まず空打ち回数を統計に残す。空打ちの罰を追加する場合も、ノーツを消費するかどうかは別の仕様として決める。

6-2. 境界を再計算しない
判定済みを配列から削除し、残ったノーツだけで中点を作り直す実装は禁止。
先に取ったノーツの区間が次へ譲られ、余分な入力が先のノーツへ流れ込むため。

6-3. 同一レーン・同時刻を禁止または統合
T[i]=T[i+1]だと区間が空になることがある。一つのキーで同時刻二ノーツをどう処理するかは別仕様。
通常4Kの最初の実装では同一レーン同時刻ノーツを譜面検証で拒否するか、一つへ統合する。
別レーン同時刻のノーツは問題ない。

6-4. 整数時刻と中点の丸め
ナノ秒やマイクロ秒などの整数時刻を使うと境界条件を再現しやすい。
中点が整数単位の半分になる場合は、丸め方を固定する。
正確に比較したいなら、オーバーフローしない範囲で2*tとT[i]+T[i+1]を比べる方式もある。
無造作に浮動小数点のepsilonを入れると所属が曖昧になる。時間単位と丸め規則を先に決める。

6-5. 入力時刻と自動MISSの処理順
入力イベントを時刻順に処理する。
各イベントの時刻まで自動MISSを進め、押下を判定し、フレーム内のイベント全部の後で現在時刻まで自動MISSを進める。
フレーム現在時刻まで先にMISSを確定すると、キュー内の有効な過去入力を取りこぼし得る。
ここで使うイベント時刻は音声／譜面時計と同じ時刻軸へ変換しておく。
入力にオフセットを適用するなら、自動MISS側も同じ補正規約で整合させる。遅れて届く入力をどこまで待つかという締切の扱いも必要。
更新ポーリングしかできず押下の発生時刻を取得できない場合、過去時刻を勝手に推定しない。実際に得られる精度を把握する。

6-6. 入力精度は高速縦連の境界に直結
例えば担当幅が±20msになる譜面では、60Hzポーリングの約16.7msは無視しにくい。
描画FPSを上げることと、押下時刻を正しく取ることは別。
Press/Releaseの遷移を使い、キーリピートは連打に数えない。
高速押下・解放が二つの更新の間で起きると状態ポーリングでは見逃し得るため、入力APIを検証する。

6-7. パターン接続の境界も計算対象
パターンを別々に判定すると、前パターンの最後と次パターンの最初の間の中点を失う。
レーンごとに次パターンの最初のノーツを確認して、前の最後の右境界まで確定する。
ノーツが画面に出る前、かつ早い側の判定が始まる前に、次のランダムパターンを決める。
プレイ中に既に有効になった担当範囲を後から変更しない。

6-8. リプレイと再現性
乱数seed、譜面、BPM、判定幅、対応付け方式、オフセット、時刻丸め規則、入力イベント列を保存する。
判定ロジックを描画から独立させれば、同じイベント列で比較しやすい。
実時間のノーツ時刻が決まってから境界を作る。将来のBPM変化では拍の単純中点と時間の中点が一致しない場合がある。

6-9. ホールドへ安易に拡張しない
今回は通常ノーツの押下のみ。
ホールドを導入すると、頭の打鍵、保持状態、解放、同じレーンの後続ノーツをどう扱うかが別途必要になる。
ホールド終了時刻を単押しと同じ列に混ぜて中点計算する、という変更は避ける。

【7. 初期検証ケース】
・1000/1100/1200msで境界1049、1050、1051msの所属。
・1000msを見逃し、1090msで1100msを拾えること。
・1000msを取得後、1040msの余分な入力が1100msを取らないこと。
・同一区間の二回押下が一成功だけになること。
・複数の見逃し後も現在の担当ノーツへ直接復帰すること。
・成功幅の端は成功、その外は無視、境界では後のノーツになること。
・疎な譜面の判定範囲間の空白を無視すること。
・不等間隔で左右の受付幅が異なること。
・トリルはレーンごと、同時押しは別レーンへ独立に対応すること。
・同一レーン同時刻を拒否または統合できること。
・パターン接続で中点が欠けないこと。
・リプレイ、フレーム停止、複数イベント一括取得でも結果が変わらないこと。
・高速縦連で低評価領域が消えること、細かな連打の得点傾向を確認すること。
テスト用人工時刻でロジックを検証し、Windows実機では入力精度とプレイ感を別に確認する。

【8. 今回のおすすめ初期仕様】
・通常ノーツだけの固定4K。
・中点は元の譜面から事前計算して固定。
・中点ちょうどは後のノーツを担当。
・担当範囲かつ成功幅内のPendingノーツだけ成功判定。
・判定済み／成功幅外への入力は無視し、先のノーツへ回さない。
・受付終了したPendingノーツは自動MISS。
・成功評価は固定msの誤差で決める。
・ノーツID、入力時刻、誤差、空打ち、見逃しを記録。
この案ならCHUNITHMの中点分割の発想を活かしながら、狙った復帰挙動を小さな実装で確認できる。
