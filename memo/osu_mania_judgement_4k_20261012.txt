固定4Kゲームの判定設計：osu!maniaの公開実装とミスハマり
調査日：2026-10-12

【結論】
ppy/osu（osu!lazer）の通常ノーツでは「同じレーンの最古の未判定ノーツに、いつまでも入力を割り当てる」という方式を採っていない。
前のノーツの打鍵受付は、次のノーツの開始時刻で打ち切られる。次のノーツを成功判定すると、それより前の未判定ノーツは強制MISSになる。
このため、最初を見逃しても、後続ノーツの予定時刻以降に正しく押せば、入力が古いノーツに吸われ続ける状態から復帰できる。
ただし最近傍ノーツを選ぶ方式ではなく、次のノーツより少し早く押した場合は前のノーツが入力を取ることがある。ミスハマりを完全に排除する保証ではない。

【1. 調査範囲とバージョン】
引き継ぎtxtに記載された https://github.com/ppy/osu を参照した。
対象はC#で公開されているosu!lazer。旧osu!stableのバイナリ内部実装を確認したわけではない。Classic Modの判定幅があっても、stableの全挙動が同じだと断定しない。
調査対象コミット：e30e332ab6bc4bbb89394f08e2ba5c58855483ec
最初にmasterを読み、主要ファイルをこのコミットで取り直して照合した。
コードと公式テストを読んだ静的調査。osu!本体のビルド・公式テスト実行・Windows実機でのプレイ検証は行っていない。
以下では通常の単押しノーツを中心に説明する。ホールドは別処理がある。

【2. なぜ「最古の未判定」だけではミスハマりが起こるか】
同じレーンのノーツ時刻が1000、1100、1200、1300msとする。
1000msを押し損ね、1110msで1100msのノーツを押すつもりだったとする。
最古の未判定を無条件に選ぶと、入力は1000msのノーツに対応し、誤差は+110msになる。これが低評価またはMISSで入力を消費すると、1210msの入力が1100msのノーツに対応する、といった一つずれが続く可能性がある。
ここで必要なのは、判定幅の調整だけでなく「この入力をどのノーツに対応させるか」という対応付けの規則。
なお実際に連続MISSになるか、低評価が連続するか、自然に復帰するかは、ノーツ間隔、成功判定幅、MISS受付幅、自動MISS期限によって変わる。

【3. 入力対象を制限するOrderedHitPolicy】
Column.cs：各レーンが独立にOrderedHitPolicyを持ち、ノーツのCheckHittableへIsHittableを登録する。
OrderedHitPolicy.IsHittable：AliveObjects上の次のノーツを取得し、「次がない、または入力時刻が次のStartTimeより小さい」場合だけ受付を許可する。
要点を式にすると、前のノーツA、次のノーツBについて
  Aへの打鍵を許可する条件：入力時刻 < Bの予定時刻
等号ではAを許可しない。Bの予定時刻ちょうどからBへ復帰できる。
ここでの「次」は生存中オブジェクトの開始時刻順であり、単純に「次の未判定ノーツ」と置き換えた説明ではない。
またこのチェックで打鍵を拒否することと、AのMISSを即座に確定することは別。境界時刻に達しただけでIsHittableがMISSを付けるわけではない。

【4. 後続ノーツ成功時の過去ノーツの処理】
Column.OnNewResultは成功判定（result.IsHit）を受けたときだけHandleHitを呼ぶ。
OrderedHitPolicy.HandleHitは、成功したノーツのStartTimeよりEndTimeが前にある先行オブジェクトを開始時刻順に調べ、まだJudgedでなければMissForcefullyを呼ぶ。
通常ノーツではEndTimeとStartTimeが同じだから、「後のノーツが成功したら、取り残された前のノーツはMISSとして清算する」と理解できる。
ホールドでは終了時刻とネストしたオブジェクトも関わるため、この単純化をそのまま使わない。
入力によるMISSでは、この成功時の清算処理は呼ばれない。先行ノーツはそれぞれの自動MISS等で処理される。

【5. 実際の入力の流れ】
HitObjectContainer.Compareには、早いノーツが先に入力を処理するよう並べる説明と実装がある。
DrawableNote.OnPressedは、レーンに対応するActionかどうかを確認し、CheckHittableを通った場合にUpdateResult(true)を呼ぶ。
DrawableHitObject.UpdateResultは判定済みならfalseを返し、未判定ならCheckForResultを呼んで、判定が確定したかを返す。
通常ノーツのCheckForResult(true, offset)はHitWindows.ResultForで結果を得る。Noneなら未処理のまま、Perfect～MehまたはMissなら判定を確定する。
したがって、早いノーツが受付可能で、入力によって結果が付くなら、その入力を取る。古いノーツがnote lockで拒否されるか、既に判定済みか、受付範囲外なら、後のノーツに処理の機会が回る。
「常に一番近いノーツを探している」という実装ではない。

【6. 判定幅：成功、入力MISS、自動MISSは分ける】
HitWindows.ResultForは誤差の絶対値を取り、PerfectからMissへ順番に比較して、条件を満たす最も良い判定を返す。範囲外はNone。
HitWindows.CanBeHitは「誤差 <= 最も広い成功判定の幅」を返す。maniaでは最も広い成功判定がMeh。
DrawableNote.CheckForResult(false, offset)はCanBeHitがfalseになるとApplyMinResultで自動MISSにする。

通常lazer、OD=5、速度倍率1、難易度倍率1、Classic無効での片側幅：
  Perfect 19.5ms
  Great   49.5ms
  Good    82.5ms
  Ok     112.5ms
  Meh    136.5ms
  Miss   173.5ms
いずれも中心から片側の幅。全幅ではない。境界はResultFor内で <=。
ManiaHitWindowsは基準幅に倍率を掛け、floorして0.5を加える。上記はOD=5の例で、他のODやMODにはそのまま使わない。

入力が136.5～173.5ms早い場合はMissになり得る。173.5msより早ければNoneで、そのノーツの判定を付けない。
見逃しの自動MISSは、更新時に遅れが136.5msを超えたところで起きる。173.5msまで待つ処理ではない。
ResultFor自体は早い側・遅い側に対称だが、通常ノーツは自動MISS期限とnote lockの制約も受ける。遅い側も173.5msまで未判定で残る、と解釈するのは誤り。
厳密な判定確定時刻にはゲーム更新や入力処理順も関わる。
Classic有効かつScoreV2無効では、最高判定の基準が16msになる等の分岐がある。今回の主題である対応付けは、判定幅の式とは別にOrderedHitPolicyにある。

【7. 公式テストが示す復帰の例】
TestSceneOutOfOrderHits.TestPreviousHitWindowDoesNotExtendPastNextObject：
・同一レーンに1000、1100、1200、1300、1400、1500、1600msの通常ノーツを置く。
・最初の1000msは押さない。
・以降はそれぞれ予定時刻+10msで押して、+11msで離す。
・期待結果：最初はMiss、後続6個はすべてPerfect。各後続の誤差は+10ms。
これは「一つ見逃しても、その後の入力が古いノーツに吸われ続けない」挙動を直接確認するための既存テストと読める。
ただし今回このテストを実行したわけではない。

【8. 早押しでは何が起こるか】
OD=5の通常lazer設定、1000msのAを見逃し、1100msのBを押す状況を考える。
  入力1090ms：Aには+90ms、Bには-10ms。
              1090 < 1100だからAはまだ受付可能。先にAが入力を処理し、Okになる。
              Bの方が時刻として近くても、BのPerfectにはならない。
  入力1100ms：Aは次ノーツの開始時刻に達して受付不可。Bは誤差0でPerfect。
              B成功に伴い、Aは強制Missになる。
  入力1110ms：同様にAは受付不可。Bは+10msでPerfect、Aは強制Miss。
この例はコードから導いた挙動であり、追加の実機テスト結果ではない。
したがって、lazerの仕組みは遅れた古いノーツへの吸着を抑えるが、早押しで一つずれが続くケースまで完全に防ぐものではない。
ノーツを一つ抜かしたのか、直前のノーツを遅く押したのかは、単一の入力時刻から一意には決められない。

【9. トリルと縦連の違い】
判定ポリシーはレーン単位。
縦連では同じレーンのノーツ間隔がそのまま対象選択の境界になる。
二つのレーンが交互に出るトリルでは、他レーンの次ノーツは境界にならない。同じレーンの次ノーツが境界になる。
例：全体のノーツ間隔75msで左右交互なら、各レーンの間隔は150ms。
他レーンのMISSが直接こちらの入力対象をずらすわけではないが、演奏の位相がずれることで両レーンの早押し・遅押しが続くことはある。
キーを押し続けている状態と、新たな押下イベントも区別する必要がある。通常ノーツは押下で判定し、離したときには判定を付けない。

【10. 自作4Kへの実装案】
最初に分離するもの：
・判定幅：対象ノーツが決まった後、誤差から評価を決める。
・対応付けポリシー：どのノーツへ入力を渡すかを決める。
・見逃し期限：未判定のまま残ったノーツをいつMISSにするかを決める。

案A：lazerを参考にした開始時刻での切り替え
各レーンに時刻順の通常ノーツ列を持つ。
入力時刻tで候補を開始時刻順に見る。
  1. 判定済みは除外。
  2. 次の譜面ノーツが存在してt >= 次の予定時刻なら、その候補は打鍵対象から除外。
  3. 成功判定幅／入力MISS幅を調べる。範囲外なら入力を消費しない。
  4. 結果が付いたら、その入力による処理を終了。
  5. 成功した場合は、それより前に取り残された通常ノーツをMISSで清算。
更新時には、遅い側の成功幅を超えた未判定ノーツを自動MISS。
これは通常ノーツ向けの設計要約。osu!のAliveObjects、プーリング、ホールド、リプレイを完全に再現するコードではない。
打鍵対象から除外することと、MISS確定を別の操作にすると元実装との関係が分かりやすい。

案B：練習用として最近傍の成功可能ノーツを選ぶ
入力時刻tについて、同じレーンの未判定ノーツのうち、成功幅内にあるノーツを候補にする。
その中から |t - ノーツ時刻| が最小のものを選び、同距離なら前のノーツを選ぶ等の規則を固定する。
選んだノーツを成功判定し、それより前の未判定通常ノーツはMISSにする。
候補がなければ空打ちとして無視。広い早押しMISS範囲は、この案では最初は設けない。
自動MISSは別に処理する。
この案なら1090msの例でBを拾えて復帰しやすい。これは自作向けの提案であり、osu!maniaの実装ではない。
各ノーツの成功幅が同じなら、競合している二つのノーツの対象切り替えは中点になる。
ただしノーツ間隔が狭いと、直前のノーツを遅く押したつもりでも次を拾い得る。例えば1000/1100msで入力1060msなら次が近い。
最近傍はプレイヤーの意図を正確に推定する保証ではなく、復帰のしやすさを優先する規則。
キー連打が有利になるか、リズムが一つずれたのに高評価になりすぎないかも確認する。

今回の短いパターンを練習する4Kなら、案Aと案Bを切り替えて比較できる設計が向いている。
最初は通常ノーツ限定で案Bを試し、既存音ゲーに近い操作感が欲しければ案Aと比較する。最高判定幅は対応付けとは別に維持できる。
表示するMISS数だけでなく、各入力の誤差と対応したノーツIDを保存すれば、「実際にリズムが乱れた」「対象選択で連鎖した」を区別しやすい。

【11. Go向けの状態と処理順】
ChartNote { ID, Lane, ScheduledTime }：譜面側の不変データ。
NoteState { Pending/Hit/Miss, Result, InputTime, Offset }：プレイ状態。
InputEvent { Lane, Press/Release, Timestamp, Sequence }：入力イベント。
レーンごとに未処理範囲を保持し、描画から独立した判定関数へイベントを渡す。ノーツごとのgoroutineは不要。

入力は発生時刻順に処理する。入力時刻が取れるなら、フレームの現在時刻で一律に置き換えない。
キューに古い入力があるのに、現在の表示時刻まで先に自動MISS処理すると、本来有効な入力を取りこぼし得る。
各イベントの時刻まで自動MISSを進めてからそのイベントを処理し、そのフレームの入力を全部処理した後で現在時刻まで進める方式が基本候補。
同時刻の扱い、成功幅の境界、入力遅延補正後の時刻軸も統一する。
通常キーの押下遷移だけを使い、OSのキーリピートで押しっぱなしが連打に化けないようにする。
自作で音声時計と入力時計をどう対応させるかは別の実装課題で、今回のソース調査だけでは解決しない。

【12. 必要な検証ケース】
・同じレーン100ms間隔、最初を抜かして以後+10ms：案Aで復帰するか。
・同じレーン100ms間隔、最初を抜かして以後-10ms：案Aと案Bの違い。
・前と次の中点の前後、次の予定時刻の前後、各判定幅の境界。
・複数ノーツを抜かしてから復帰するケース。
・トリル：レーン別の判定であること。
・異なるレーンの同時押し：一つの入力が他レーンを消費しないこと。
・押しっぱなし、キーリピート、素早い押下と解放。
・フレーム停止後に複数入力をまとめて処理するケース。
・高速縦連で一つの押下が二つの成功を作らないこと。
・BPM変更でノーツ間隔と幅が重なる程度が変わること。
判定ロジックに人工のノーツ時刻・入力時刻を渡すテストと、Windowsでの体感評価を分ける。
